## 🕒 นาทีที่ 1:30 - 3:30 | Transport Layer & Characteristics
**[Slide 2: ทำไมถึงเลือกใช้ UDP?]**
"Application ของเรามี Characteristic แบบ **Real-time, High-speed Data Transmission** ครับ ข้อมูลพิกัดเครื่องบินเปลี่ยนตลอดเวลา ดังนั้นเราจึงเลือกใช้ **UDP** ใน Transport Layer ด้วยเหตุผล 3 ข้อหลักครับ:"

1. **Low Latency:** เราไม่ต้องการเวลาที่เสียไปกับการทำ 3-Way Handshake ของ TCP เพราะเสี้ยววินาทีก็มีผลต่อการชนครับ
2. **Tolerance to Packet Loss:** สมมติพิกัดวินาทีที่ 1 หายไป TCP จะพยายาม Retransmit ส่งพิกัดเก่าซ้ำ ซึ่งมัน Outdated ไปแล้ว แต่ UDP เรายอมทิ้งเลย แล้วรอรับพิกัดใหม่ในวินาทีที่ 2 แทนครับ ซึ่ง Make sense กว่า
3. **No Head-of-Line Blocking:** เราไม่ต้องกังวลว่า Packet ที่มาทีหลังจะต้องรอ Packet ก่อนหน้าที่หายไปครับ

## 🕒 นาทีที่ 3:30 - 5:30 | Protocol Design & Separation Rules
**[Slide 3: Request & Response Format]**
"สำหรับ Application-Layer Protocol ที่ออกแบบไว้ จะสื่อสารกันเป็น Text-based ผ่าน Format นี้ครับ"
*(ชี้ที่สไลด์)*
- **Request (เครื่องบิน -> Server):** `TCASP/1.0 PING <seq_no> <flight_ID> <posX> <posY> <posZ>`
- **Response (Server -> เครื่องบิน):** `TCASP/1.0 <seq_no> [<flight_ID>] <Status_Code> <Status_Phrase>`

"จุดเด่นแรกเลยคือ **มีการใช้ Versioning (TCASP/1.0) และ Sequence Number** เพื่อรองรับการอัพเกรดในอนาคตและตรวจจับ Packet Loss ครับ"

**[Slide 4: Status Code]**
"ระบบจะอ้างอิงพิกัด 3 มิติ (X, Y, Z) โดยมีระยะปลอดภัยคือ ห่างกันเกิน 2.0 ไมล์ทะเล (แนวนอน) หรือ ความสูง (Y) ห่างกันเกิน 1000 ฟุต"
- `200 CLEAR`: ปลอดภัย
- `300 TA_TRAFFIC`: เข้าใกล้เกิน 5.0 ไมล์ (แจ้งเตือนให้ระวัง)
- `401 RA_CLIMB` / `402 RA_DESCEND`: อันตราย! เข้าใกล้เกิน 2.0 ไมล์ เครื่องนึงต้องเชิดหัวขึ้น อีกเครื่องต้องปักหัวลง (posY ± 1000)

## 🕒 นาทีที่ 5:30 - 7:30 | 🏗️ Architecture Comparison: Client-Server vs P2P
**[Slide 5: เปรียบเทียบสถาปัตยกรรม]**
"เพื่อให้เห็นภาพกว้างขึ้น ผมขอเปรียบเทียบระบบ TCASP (ที่เป็น Client-Server) กับระบบ TCAS ของจริง (ที่เป็น Peer-to-Peer หรือ P2P) ครับ"

"**ระบบ TCAS ของจริง (P2P):** เครื่องบินแต่ละลำจะส่งสัญญาณ (Broadcast) หากันเองโดยตรง"
- **ข้อดี:** ไม่ต้องพึ่งพา Server กลาง ถ้าเครื่องไหนบินไปในจุดอับสัญญาณภาคพื้นดิน ก็ยังหลบกันเองได้ (No Single Point of Failure)
- **ข้อเสีย:** เครื่องบินทุกลำต้องมีอุปกรณ์ประมวลผลที่ทรงพลังมาก และการส่งสัญญาณหากันเองจะวุ่นวายมากเมื่อมีเครื่องบินหนาแน่น (Network Congestion)

"**ระบบ TCASP ของเรา (Client-Server):** เครื่องบินส่งข้อมูลหา Server และ Server คำนวณให้"
- **ข้อดี:** เครื่องบินไม่ต้องรับภาระการประมวลผลเลย (Lightweight Client) Server กลางสามารถมองเห็นภาพรวม (Global View) ได้ดีกว่า ทำให้สามารถวางแผนหลบหลีกให้เครื่องบินเป็นร้อยๆ ลำพร้อมกันได้อย่างเป็นระเบียบ
- **ข้อเสีย:** ถ้า Server ล่ม (Single Point of Failure) เครื่องบินทุกลำจะตาบอดทันทีครับ

"การที่เราเลือกทำแบบ Client-Server เพราะมัน Scale ง่าย และเหมาะกับการทำ Centralized Air Traffic Control ในปัจจุบันครับ"

## 🕒 นาทีที่ 7:30 - 9:30 | ✨ จุดเด่นของโปรเจค (Highlights เพื่อคะแนน)
**[Slide 5: ความท้าทายและจุดเด่น]**
"เพื่อให้ออกมาดีที่สุด ผมได้ออกแบบฟีเจอร์เพิ่มเติมที่เหนือกว่าแค่ Client-Server ทั่วไปครับ:"

1. **Multi-Threading Client:** โค้ดฝั่งเครื่องบินไม่ได้ทำงานเป็นลูปเดียวแบบ Sleep บล็อคกันครับ ผมเขียนแยก Thread ชัดเจน *Thread ส่ง* ก็ส่งพิกัดไป *Thread รับ* ก็คอยฟังคำเตือนตลอดเวลา ทำให้มันตอบสนองแบบ Real-time และแก้ปัญหา Message หายครับ
2. **N-Aircraft Support:** Server ไม่ได้ล็อคไว้แค่เครื่องบิน 2 ลำครับ ผมเขียน Algorithm วนลูปจับคู่เช็ค (Pairwise) แปลว่าเราจะต่อ Client เข้ามากี่ร้อยลำ Server ก็สามารถจัดการและคำนวณ Conflict ได้หมดครับ
3. **Safety-Aware Notification:** เวลาเกิดอันตราย (TA/RA) Server จะยิงแจ้งเตือนกลับไปยังเครื่องบิน **ทั้งสองลำพร้อมกันทันที** ครับ ไม่ใช่ส่งแค่ลำที่ PING เข้ามา เพื่อให้ทั้งคู่รู้ตัวพร้อมกัน แต่ตอนที่สถานะ CLEAR จะตอบกลับแค่ลำเดียวเพื่อประหยัด Bandwidth ครับ

## 🕒 นาทีที่ 7:30 - 9:30 | 🧑‍💻 อธิบายโค้ดส่วนสำคัญ (Code Walkthrough)
**[Slide 6: โครงสร้าง Code]**
"ก่อนจะไปดู Demo ผมขออธิบายโครงสร้างโค้ดที่ทำให้เกิดฟีเจอร์เด่นๆ เหล่านี้ครับ"

**ส่วนของ Server (tcasServer.py):**
- "หัวใจสำคัญอยู่ที่การใช้ `itertools.combinations` หรือการเขียน `for i` ซ้อน `for j` เพื่อเปรียบเทียบระยะห่างของเครื่องบินทุกๆ ลำที่เชื่อมต่อเข้ามา (Pairwise) ไม่ว่าจะมีกี่ลำก็จะถูกเช็คระยะต่อกันหมดครับ"
- "นอกจากนี้ผมยังดัก `try-except ValueError` เอาไว้ตอนแปลงค่าพิกัด เพื่อป้องกันไม่ให้ Server พังถ้า Client เผลอส่งข้อมูลผิดรูปแบบมาครับ (Graceful Degradation)"

**ส่วนของ Client (tcasClient.py):**
- "Client ผมเขียนรวมเป็นไฟล์เดียวเลย แล้วใช้ `argparse` รับค่าพิกัดเริ่มต้น ทำให้เราสามารถสร้างเครื่องบินกี่ลำก็ได้จาก Command Line"
- "ส่วนของ Threading ผมใช้ `threading.Thread(target=receive_loop)` แยกให้ Thread นึงทำหน้าที่ `recvfrom` รอรับการแจ้งเตือนจาก Server ตลอดเวลา ส่วน Main Thread ก็ทำหน้าที่ PING ส่งพิกัดและคำนวณการหลบหลีก (RA) ไปครับ ทำให้ไม่มีการทำงานที่บล็อคกันเลย"
